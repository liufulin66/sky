# 用户端下单与订单查询

本次实现提交订单、历史订单分页和订单详情。全部要求 `authentication: <用户JWT>`，用户身份只取 BaseContext，客户端不能指定订单用户、订单号或支付状态。

直连 `http://localhost:8080`；当前 Nginx 为 `http://localhost:90`，用户端路径不加 `/api`。成功返回 `code=1`；业务失败返回 `code=0` 和 `msg`；JWT无效返回HTTP401。

## 先执行数据库迁移

应用依赖 [2026-10-15-user-orders.sql](../sql/migrations/2026-10-15-user-orders.sql)。应用不会自动执行迁移；先备份并审阅，在目标数据库手动执行一次。先检查重复订单号，存在冲突须人工处理，不自动改写历史订单。

迁移内容：订单id改为自增；订单号唯一；新增 `request_id`、`request_hash` 和配送费快照；同一用户的requestId唯一；收货人长度扩为50、完整地址扩为512；增加历史订单和明细查询索引。旧订单的幂等字段为NULL、配送费默认为0，不改变原金额。

已有数据库和新导入的基线数据库都要执行该迁移。不要用包含DROP TABLE的完整建表文件覆盖已有业务库；迁移执行成功后不要重复执行。

## 接口

| 方法和路径 | 参数 | 成功 data |
| --- | --- | --- |
| `POST /user/order/submit` | JSON，下文示例 | id、orderNumber、orderAmount、orderTime |
| `GET /user/order/historyOrders` | page默认1，pageSize默认10，status可选 | total、records（OrderVO数组） |
| `GET /user/order/orderDetail/{id}` | 正整数订单id | OrderVO，包含orderDetailList |

历史订单按下单时间、id降序。page必须为正整数；pageSize为1～100；status支持实体定义的1～6，不传查询全部。空结果records为[]，超出页数时保留实际total。列表与详情只查询当前用户，访问不存在或他人订单统一提示“订单不存在或无权查看”。

## 提交订单示例

```json
{
  "requestId": "d01b88de-70d8-4b8e-bc88-cacdbb8b21e5",
  "addressBookId": 1,
  "payMethod": 1,
  "remark": "请送到门口",
  "deliveryStatus": 1,
  "tablewareStatus": 1,
  "packAmount": 0,
  "amount": 50.00
}
```

- requestId必填，1～64位字母、数字、下划线或短横线，推荐前端生成UUID。同一次操作及网络重试保持该值和表单不变；重新下单或修改表单时生成新值。
- addressBookId必填且为本人地址，不强制使用默认地址。
- payMethod必填，1微信、2支付宝；这里只保存选择，本次不调用支付平台，也不把订单标记为已付款。
- remark可选，去掉首尾空白，最长100字符。
- deliveryStatus不传默认1（立即配送）；立即配送不使用客户端预计时间。传0表示预约，必须同时传 `estimatedDeliveryTime`，格式 `yyyy-MM-dd HH:mm:ss`，首次提交时必须晚于服务端当前时间；目前不限制预约日期范围，也不计算路线或承诺送达时限。
- tablewareStatus不传默认1（按餐量提供），数据库数量记0，由厨房依据订单内容提供；传0时必须填写非负整数tablewareNumber，0表示不要餐具。
- amount必填，为用户确认的订单总额（元）；金额非负且最多两位有效小数，总额不得超过99999999.99。后端不使用客户端金额决定商品售价。
- packAmount可选，沿用整数元；如提供，必须与后端打包费一致。

## 计价与商品检查

`sky.order.pack-amount` 为固定每单打包费（非负整数元），`sky.order.delivery-amount` 为固定每单配送费（非负、最多两位有效小数），两者默认0。在application.yml配置，启用非零费用时，小程序结算页需同步展示并计入用户确认的总额。

```text
订单总额 = Σ（数据库商品单价 × 购物车数量） + 打包费 + 配送费
```

新增订单检查营业状态、本人地址、非空购物车及正整数数量。商品价格、名称和图片直接读DishMapper/SetmealMapper，不读取商品浏览缓存，也不采用购物车旧单价。菜品分类必须启用且类型正确；套餐关联菜品缺失或停售时不能下单。

金额或打包费不一致时返回“商品价格或费用已变化，请刷新结算页后确认”，不生成订单、不清空购物车，不自动按涨价后的金额成交。地址/商品不可用、店铺打烊、参数异常也拒绝首次下单。

当前项目无库存字段，不做虚构库存扣减。商品校验采用本次数据库事务读取到的商品版本；用户行锁协调该用户的购物车/地址/下单，不锁定商家商品维护，也不保证“商家下架提交后，所有尚未提交的订单一律失败”。

## 事务、快照与幂等

- 下单先锁已有用户行，随后查询幂等记录，再检查营业、地址和购物车；与已有购物车、地址簿写操作使用同一用户锁，避免结算期间新增商品被误清理。
- 在同一事务中写订单主表、批量写明细、清空当前用户整份购物车。任何一步失败整体回滚，失败请求不占用requestId，可在修正问题后重试。
- 新订单为待付款status=1、未支付payStatus=0。checkoutTime不设置。事务提交成功后才向客户端返回成功。
- 主表保存下单时的收货人、电话、完整地址、总额和费用；明细amount为成交单价，number为数量，保存名称、图片和口味。历史订单只读这些快照，不会因商品改价或地址变更而重算。
- 同一用户相同requestId和规范化表单重复提交，返回原订单的提交结果，不再次检查当前价格、地址、营业状态或购物车，不清空重试前新加入的商品。
- 请求摘要由JDK的SHA-256生成，输入按字段长度编码，金额规范为两位小数、文本去掉首尾空白、配送与餐具选择规范化。摘要用来区分重试与错误复用键，不代替用户鉴权。
- 相同requestId但不同表单返回业务错误；不同用户可以使用相同requestId。数据库唯一约束是最终保障。不能仅靠生成不同订单号来识别重复提交。
- requestId是这次结算操作的身份，重试时不要将它用于新购物车。幂等字段和摘要不向订单列表/详情暴露。

## 小程序调用顺序

1. 刷新地址和购物车，展示本次金额。
2. 为本次提交生成requestId，发送表单；超时后按原表单和requestId重试。
3. 成功后保存订单id/订单号，刷新购物车，进入待付款订单页面。
4. 通过历史分页或详情查看订单。当前不提供真实支付、取消、退款、再来一单或商家接单接口。

## 验证

常规测试：`mvn -o -pl sky-server -am test`。

本地 MySQL 集成测试：`mvn -o -pl sky-server -am test '-Dorder.mysql.tests=true'`。读取本地application-dev.yml，只创建随机ord_test_前缀测试表；从基线建表文件提取CREATE语句并执行生产迁移，再加载生产Mapper和真实Spring事务/HTTP分派。验证迁移约束、重算价格、用户隔离、快照、并发重试、事务回滚和分页；结束后清理自身测试表，测试不修改业务表或已有订单。营业状态用测试替身隔离，不依赖Redis服务。

# 商家端订单管理

本模块提供接口文档中的8个接口。直连后端时使用 `http://localhost:8080/admin/order`，全部要求管理端请求头 `token: <管理员JWT>`。用户JWT不能访问这些接口。当前项目是单店模型，管理员查询整个店铺的订单，不按管理员员工id筛选下单用户。

成功为 `code=1`；业务失败为 `code=0` 并返回 `msg`；管理端JWT缺失或无效返回HTTP401。拒单按当前约定只执行参数、订单存在性和状态校验，不执行已支付订单的拒单或退款。

## 接口和参数

| 方法和路径 | 参数 | 成功data |
| --- | --- | --- |
| `GET /admin/order/conditionSearch` | 查询参数，见下文 | `total`、`records` |
| `GET /admin/order/details/{id}` | 正整数订单id | `OrderVO`，包含商品明细 |
| `GET /admin/order/statistics` | 无 | `toBeConfirmed`、`confirmed`、`deliveryInProgress` |
| `PUT /admin/order/confirm` | JSON：`{"id":9}` | null |
| `PUT /admin/order/delivery/{id}` | 正整数订单id | null |
| `PUT /admin/order/complete/{id}` | 正整数订单id | null |
| `PUT /admin/order/cancel` | JSON：`{"id":9,"cancelReason":"商品售罄"}` | null |
| `PUT /admin/order/rejection` | JSON：`{"id":9,"rejectionReason":"无法配送"}` | 当前阶段返回业务失败 |

取消和拒单的原因去除首尾空白后必须为1～255个字符。接单只读取JSON中的id，忽略客户端传入的status，目标状态由服务端决定。派送、完成的id只读取路径；用户端取消仍为 `PUT /user/order/cancel/{id}`，不要混用两端接口。

## 订单搜索、详情和数量

搜索参数：

| 参数 | 规则 |
| --- | --- |
| page | 默认1，正整数；分页偏移量不能超出32位整数范围 |
| pageSize | 默认10，范围1～100 |
| number | 可选，去除首尾空白，最长50字符，订单号包含该文本 |
| phone | 可选，去除首尾空白，最长11字符，收货手机号包含该文本 |
| status | 不传或传0查询全部；有效订单状态为1～6 |
| beginTime | 可选，下单时间大于等于此值 |
| endTime | 可选，下单时间小于等于此值 |

时间格式为 `yyyy-MM-dd HH:mm:ss`，起止时间都传时不能颠倒。空白搜索文本视为未传，多个条件按AND组合。客户端传入userId不参与筛选。

查询条件接收精确到秒的时间；响应中的订单时间沿用项目全局格式 `yyyy-MM-dd HH:mm`，数据库保留秒精度。

例如查询订单号包含123、手机号包含138的待接单订单：

```text
GET /admin/order/conditionSearch?page=1&pageSize=10&number=123&phone=138&status=2
```

模糊匹配使用MyBatis参数绑定，用户输入的 `%`、`_`、`!` 转义后按普通字符匹配，不能作为通配符扩大查询范围。订单先按下单时间倒序，再按id倒序，保证同一时间的订单排序稳定。空结果返回records=[]，超出总页数时仍保留真实total。

分页主表查询由PageHelper处理，包括总数查询和当前页查询；随后用当前页的订单id一次性查询所有明细并分组，避免每条订单再查一次数据库。空页不执行明细IN查询。详情复用相同明细组装方式，读取成交价格、名称、地址等订单快照，不重新读取商品当前价格。requestId和requestHash不向客户端暴露。

数量接口覆盖全部日期，只返回管理端待处理标签需要的三项：

```json
{"code":1,"msg":null,"data":{"toBeConfirmed":2,"confirmed":1,"deliveryInProgress":3}}
```

分别对应状态2待接单、3待派送、4派送中；不是返回1～6每一种状态的计数。一次SQL条件聚合即可取得三项数量，无订单时均为0。统计按订单status计数，不额外按payStatus过滤；异常历史订单不会被静默隐藏，状态操作仍会检查支付状态。

## 状态流转和重复操作

| 操作 | 允许的原状态和支付状态 | 更新结果 |
| --- | --- | --- |
| 接单 | 2待接单、1已支付 | status=3已接单 |
| 派送 | 3已接单、1已支付 | status=4派送中 |
| 完成 | 4派送中、1已支付 | status=5已完成，deliveryTime记录当前时间 |
| 商家取消 | 1待付款、0未支付 | status=6已取消，保存cancelReason、cancelTime |
| 拒单 | 校验订单为2待接单、1已支付 | 提示“暂未接入退款，无法拒单”，不修改数据 |

同一操作重复到达其目标状态时返回成功。例如订单仍处于已接单状态，重复接单成功；已经派送或完成时再接单返回错误，不允许状态倒退。完成订单的重试不覆盖第一次送达时间。已取消且未支付的订单再次取消成功，不覆盖原取消原因和时间，无论第一次由用户还是商家取消。

商家取消已支付订单提示“暂未接入退款，无法取消已支付订单”；不将已收款订单直接取消、不把payStatus改为退款。已退款或其他不符合条件的订单也不能按未付款订单取消。

## 实现原理

管理端Controller只负责绑定请求、返回统一结果，业务由独立的 `AdminOrderServiceImpl` 处理。用户端Service继续负责本人订单归属校验，避免把管理员员工id误认为用户id。没有增加新依赖。

写操作采用Spring的 `@Transactional`，在同一数据库事务中用 `SELECT ... FOR UPDATE` 锁住目标订单行，再校验支付状态及原订单状态。其他修改同一订单行的事务需要等待锁释放，防止两个请求同时依据旧状态作决定。商家不修改购物车或地址簿，因此无需锁用户行。

最终UPDATE仍携带原状态和支付状态条件，影响行数必须为1。例如接单的核心SQL为：

```sql
UPDATE orders SET status = 3
WHERE id = ? AND status = 2 AND pay_status = 1;
```

带条件更新避免把不符合状态的订单直接覆盖；行锁使校验和修改在同一事务内串行执行。事务失败自动回滚。重复请求在读取到目标状态后直接返回，保留第一次操作的时间和原因。拒单当前不写数据，因此不需要为它开启写事务。

接单、派送、完成不改变订单金额、支付状态、商品明细或购物车；取消也保留订单及明细，不把商品自动加回购物车。

## 数据库和验证

本模块复用orders、order_detail现有字段，无新增迁移SQL。已有用户下单迁移仍需按原说明执行；再来一单所需的独立迁移与本次商家订单管理无关，不要重复执行已经完成的迁移。

未接入真实支付时，正常提交的订单保持待付款，不能通过商家接单接口绕过支付。自动化测试仅在随机前缀测试表准备已支付订单，验证完整商家流程，不提供模拟付款的业务接口。

测试覆盖管理端鉴权、8个路由及参数绑定、跨用户查询与用户端归属隔离、模糊匹配转义、组合筛选与分页、历史快照、空表及跨日期数量、状态和支付状态矩阵、重复提交、拒单退款边界，以及完成/取消的并发行为。
